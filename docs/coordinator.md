# Coordinate with Switchbite

The project server `switchbite-stackbite` exposes `switchbite_start`, `switchbite_next`, and `switchbite_observe`. Give start an absolute `workspace`, a factual `pool` of workers, and either `goal` or `plan`. Each pool entry has a unique `id`, `description`, `capabilities`, and `available`; include the actual `provider`, `model`, `effort`, and `executable` for local worker execution. `resource_key` identifies a shared worker resource. Do not invent availability or model identities. Run IDs, action IDs, and scheduling defaults are generated by the engine.

A plan contains `nodes`. Each task needs `id` and `objective`; add `depends_on` task IDs, an optional `role` (`exploration`, `implementation`, `mockup`, `integration`, or `review`), `requirements`, `acceptance`, and `context_refs`. Use relative repository `write_paths` for ownership; put artifact references in `outputs`. A dependency starts only after its prerequisite is verified and integrated. Separate write paths and worker reservations allow independent work to proceed in parallel.

For a goal-only start, the returned `plan` action asks the coordinator to decompose the goal. Use the exact run and action IDs returned by the workflow. For example, send `switchbite_observe`:

```json
{"run_id":"RUN_ID","event":{"action_id":"PLAN_ACTION_ID","event_id":"plan-1","result":{"plan":{"nodes":[{"id":"build","objective":"Implement the feature","role":"implementation","depends_on":[],"acceptance":["Feature checks pass"],"write_paths":["src/feature.rs"]},{"id":"review","objective":"Review the integrated feature","role":"review","depends_on":["build"],"acceptance":["Review is complete"],"write_paths":[]}]}}}}
```

A `repair` action requests a bounded revision of unfinished work. Return a replacement task with the same ID, or a `plan` containing revised unfinished nodes. For example:

```json
{"run_id":"RUN_ID","event":{"action_id":"REPAIR_ACTION_ID","event_id":"repair-1","result":{"task":{"id":"build","objective":"Fix the failing feature check","role":"implementation","depends_on":[],"acceptance":["Feature checks pass"],"write_paths":["src/feature.rs"]}}}}
```

Call `switchbite_next` to continue. The workflow resolves `route` using the selected judge. With a local `host` configuration (for example `"host": {}`), or a pool with complete local worker metadata, it can perform supported `prepare`, `launch`, `inspect`, `verify`, `integrate`, and `gather_context` actions. Otherwise the coordinator performs those actions using its host and records results with `switchbite_observe`. `plan`, `repair`, and `review` require coordinator attention. An observation always has the exact `action_id`, a stable unique `event_id`, and an action-specific `result`; resending the identical observation is safe.

Host results use these shapes: `prepare` returns `status: prepared` plus `workspace`, `branch`, `integration_workspace`, and `integration_branch`; `launch` and `inspect` return `running`, `unknown`, `failed`, or `completed`, with an `execution_id` and `completion_verified: true` for verified completion; `verify` returns `passed` or `failed` and an `evidence` array; `integrate` returns `integrated` or `failed` and may include a commit and evidence; `gather_context` returns `gathered` and `context_refs`. Inspect an unknown execution rather than launching it again. Collect missing context and follow repair actions within the bounded repair limit.

Use next with `operation: status`, `pause`, `resume`, or `cancel` for run control. Cancellation may return actions for running work; carry them out and report results. A failed judge does not switch providers automatically. Continue execution, verification, and integration until the workflow completes or needs an actionable input. The legacy agent profile remains available for direct routing, plan validation, feedback, and status.
